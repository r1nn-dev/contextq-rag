  labels/              # E3 블라인드 레이블 (익명화 후 git 커밋)
  figures/             # 결과 그래프 (스크립트로 자동 생성)
scripts/
  eval_e1.py           # E1 실험 스크립트
  eval_e2.py           # E2 실험 스크립트
  eval_e3_generate.py  # E3 답변 생성 스크립트

- 그래프·표는 `eval/figures/` 생성 스크립트로 자동 생성한다.

## 실험 E1. 버전 격리 효과 측정

- **질문**: 버전 격리 검색이 혼입을 얼마나 줄이는가? 범위 밖 질문의 NO_CONTEXT 처리 비율은?
- **관련 ADR**: ADR-004 (버전 격리 방식: 컬렉션 분리), ADR-007 (NO_CONTEXT 임계값 τ 결정)
- **데이터**: Q-ret 40개 (혼입 측정), Q-oos 10개 (NO_CONTEXT 처리 측정)

**비교 조건**

| 조건 | 설명 | 목적 |
| --- | --- | --- |
| E1-N (비격리) | v0.3·v1.x 청크를 단일 컬렉션에 넣고 버전 필터 없이 Top-5 검색 | 혼입 발생량 측정 (격리 필요성 근거) |
| E1-F (필터) | 메타데이터 필터(`version=v0.3` 또는 `version=v1.x`)만 적용 | 비교용 |
| E1-C (컬렉션 분리) | 버전별 별도 컬렉션 직접 지정 (운영 방식) | 혼입 차단 검증 |

> E1-C가 운영 방식이다. E1-N은 격리 없을 때의 기준선이며, 혼입이 0이 아님을 보여야 E1-C의 필요성이 증명된다.

**혼입 판정 기준**: Top-K 청크 중 선택한 버전이 아닌 버전의 메타데이터(`version` 필드)를 가진 청크가 1개 이상이면 혼입으로 판정.

**NO_CONTEXT 임계값 τ 결정 절차** (E1 부속)

1. Q-ret 40개 × 두 버전 = 80회 검색에서 최대 유사도 분포 기록
2. Q-oos 10개 × 두 버전 = 20회 검색에서 최대 유사도 분포 기록
3. τ를 Q-ret 최소값과 Q-oos 최대값 사이에서 오탐·미탐 균형점으로 결정
4. 결정된 τ를 `eval/decision_rules.md`에 기록하고 운영 설정에 반영

**지표**

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 혼입률 (E1-N) | Q-ret 40회 중 비선택 버전 청크가 반환된 비율 | 수치 보고 (0이 아님을 확인) |
| 혼입률 (E1-C) | 동일 질문셋, 컬렉션 분리 적용 | **0건** |
| NO_CONTEXT 처리율 | Q-oos 10개 중 LLM 미호출 + 안내 메시지 반환 비율 | **8건 이상 (80%)** |
| τ 결정값 | 위 절차로 결정된 임계값 | 보고 |

**산출물**: 혼입률 비교표 (E1-N vs E1-C), 유사도 분포 히스토그램 (Q-ret vs Q-oos), τ 결정 근거

## 실험 E2. 청킹 전략 비교

- **질문**: 어떤 청킹 전략이 LangChain 공식 문서에서 가장 높은 검색 적중률을 보이는가?
- **관련 ADR**: ADR-003 (청킹 전략 선택)
- **데이터**: Q-ret 40개 (Gold 섹션 레이블 포함)
- **사전 조건**: `eval/decision_rules.md`에 결정 규칙을 `eval-v1` 태그 이전에 커밋 (실험 전 확정, 불변)

**비교 전략**

| 전략 | 설명 | 주요 파라미터 |
| --- | --- | --- |
| A — CharacterTextSplitter | 고정 크기 분할 | `chunk_size=1000, overlap=200` |
| B — RecursiveCharacterTextSplitter | 재귀적 분리자 계층 분할 | `chunk_size=1000, overlap=200, separators=["\n\n", "\n", " "]` |
| C — 구조 인식 (MarkdownHeaderSplitter + 코드 펜스 원자 단위) | 헤더 경계·코드 블록 비분할 | `header_levels=["#","##"], preserve_code_blocks=True` |

**사전 결정 규칙** (`eval/decision_rules.md`에 커밋, 실험 전 고정)

```
1. 기본 채택 기준: Hit@5 최고 전략을 채택한다.
2. 동률 처리: 1·2위 Hit@5 차이 < 3%p이면 평균 컨텍스트 토큰이 적은 전략을 채택한다.
3. K 결정: Hit@K 증가폭이 < 2%p인 최소 K를 운영 Top-K로 사용한다.
4. 위 규칙의 적용 순서는 1 → 2 → 3이며, 커밋 이후 변경 불가.
```

**지표**

| 지표 | K 값 | 정의 |
| --- | --- | --- |
| Hit@K | 3, 5, 8 | Q-ret 40개 중 Gold 섹션이 Top-K에 포함된 비율 |
| MRR@K | 3, 5 | 첫 번째 Gold 섹션 순위의 역수 평균 |
| Precision@K | 5 | Top-K 중 Gold 섹션 청크 비율 |
| 평균 컨텍스트 토큰 | — | Top-5 청크의 평균 토큰 수 |
| 코드 블록 보존율 | — | 전략 C만: 코드 펜스가 단일 청크 안에 완전히 들어간 비율 |

**하위 분석**: 질문 유형별(API_USAGE / CODE_PATTERN / CONCEPT / MIGRATION), 버전별(v0.3 / v1.x) Hit@5 분해

**블라인드 절차**: 전략 레이블을 가린 채 Gold 레이블링 먼저 완료 → 이후 전략별 점수 계산

**산출물**: 전략 × K 비교표, 채택 전략·운영 K 기록 (`eval/results/E2/decision.md`)

## 실험 E3. 답변 버전 정확도 비교

- **질문**: 버전 격리 RAG 시스템(R2)이 범용 LLM(L0·L1)보다 버전 오류를 얼마나 줄이는가?
- **관련 ADR**: ADR-002 (LLM 선택: GPT-4o-mini), ADR-004 (격리 방식)
- **데이터**: Q-shared 20개 × 버전 2 = 40쌍 × 조건 4 = **160답변**

**4개 비교 조건**

| 조건 코드 | 설명 | 목적 |
| --- | --- | --- |
| L0 | 범용 LLM (GPT-4o-mini), 버전 명시 없는 질문 | 가장 열악한 기준선 |
| L1 | 범용 LLM (GPT-4o-mini), 질문에 "LangChain {버전} 기준으로" 명시 | 프롬프트로 버전 통제 시도 |
| R1 | 본 시스템 RAG (버전 격리 검색), 단 NO_CONTEXT 미적용 (임계값 τ=0) | 검색 효과 단독 측정 |
| R2 | 본 시스템 RAG (버전 격리 검색 + NO_CONTEXT), 운영 방식 | 전체 시스템 효과 측정 |

> 모든 조건에서 동일 모델(GPT-4o-mini), temperature=0, 동일 프롬프트 프레임 사용. 모델이 비교 결론을 좌우하지 않도록.

**블라인드 레이블링 절차**

1. 160개 답변을 조건 레이블 없이 무작위 순서로 섞는다.
2. 두 명의 레이블러(지도교수 + 외부 1인)가 독립적으로 버전 오류 여부를 판정한다.
3. 불일치 건수와 Cohen's kappa를 보고한다.
4. 불일치 건은 논의 후 합의하여 최종 라벨을 결정한다.
5. 합의된 라벨을 기반으로 조건별 버전 오류율을 계산한다.

**레이블 항목**

| 항목 | 값 | 설명 |
| --- | --- | --- |
| `version_error` | 0 / 1 | 1 = 선택 버전이 아닌 코드·API 명시적 포함 |
| `evidence_quality` | 0 / 1 / 2 | R1·R2 조건만. 0=없음, 1=부분, 2=충분 |
| `answer_usefulness` | 0 / 1 / 2 | 전 조건. 0=무관, 1=부분 유용, 2=유용 |

**지표**

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 버전 오류율 | 조건별 `version_error=1` 비율 | R2 < L0·L1, 절대값 ≤ 20% |
| 근거 충실성 | R1·R2의 `evidence_quality≥1` 비율 | 보고 |
| 답변 유용성 | `answer_usefulness≥1` 비율 | 보고 |
| 레이블러 간 kappa | Cohen's kappa | 보고 (한계로 명시) |

**경고**: 표본 크기(20문항 × 2버전)가 작아 통계적 유의성 주장에 한계가 있다. 보고서에 "표본 크기 한계를 타당성 위협으로 명시"한다.

**산출물**: 조건별 버전 오류율 비교표, 레이블링 불일치 사례 목록, Cohen's kappa

## 실험 E5. TTFT (첫 토큰 응답 시간) 측정

- **질문**: 배포 환경에서 TTFT p50·p95가 사용성 기준을 만족하는가?
- **환경**: EC2 t3.small (배포 환경), 운영 인덱스 활성화 상태
- **측정 대상**: 단일 모드 RAG 스트리밍 (`POST /api/v1/chat`)

**측정 절차**

1. Q-ret에서 MEDIUM 난이도 질문 1개를 고정 (캐시 영향 최소화를 위해 매 측정마다 동일 질문 사용)
2. 예열 10회 실행 (결과 제외)
3. 20회 연속 측정, 각 측정 간 5초 간격
4. TTFT = 첫 `token` SSE 이벤트 수신 시각 − 요청 전송 시각

**TTFT 분해 (단계별 지연 기록)**

| 단계 | 측정 방법 |
| --- | --- |
| Spring Boot 처리 | Spring Boot → FastAPI 호출 시작까지 |
| Embedding | FastAPI 임베딩 호출 소요 시간 |
| Retrieval | Chroma 검색 소요 시간 |
| LLM TTFT | OpenAI API 첫 토큰까지 |
| SSE 전달 | FastAPI → Spring Boot → 클라이언트까지 |

> `done` 이벤트의 `latency_breakdown` 필드로 기록

**합격 기준**

| 지표 | 목표 |
| --- | --- |
| TTFT p50 | ≤ 3초 |
| TTFT p95 | ≤ 5초 |

**산출물**: 20회 측정값 분포 (박스플롯), 단계별 지연 분해표

## 실험 E6. 부하 테스트 (동시 스트림 한계)

- **질문**: EC2 t3.small에서 동시 스트림 10 VU를 처리할 수 있는가?
- **환경**: EC2 t3.small, **mock LLM 모드** (OpenAI 미호출, 고정 토큰 스트림 반환)
- **도구**: k6 (로컬 PC에서 실행, 대상 EC2와 분리)

> mock LLM 모드: `MOCK_LLM=true` 환경변수 시 FastAPI가 미리 정의된 토큰을 50ms 간격으로 스트리밍. E6 목적은 LLM 처리량이 아니라 EC2 메모리·CPU·연결 처리 한계 측정.

**시나리오 (S0~S4)**

| ID | 이름 | VU | 지속 | 목적 |
| --- | --- | --- | --- | --- |
| S0 | Smoke | 1 | 1분 | 기본 E2E 동작 확인 |
| S1 | Load | 10 | 5분 (Ramp-up 1분) | 동시 스트림 한계 측정 |
| S2 | Stress | 20 | 3분 | 한계 초과 시 동작 확인 |
| S3 | Soak | 10 | 30분 | 메모리 누수·연결 누수 확인 |
| S4 | Policy | 1 | — | 비로그인 5회 제한, 429 반환 확인 |

**지표**

| 지표 | 정의 | 목표 (S1 기준) |
| --- | --- | --- |
| 오류율 | HTTP 오류 (5xx) 비율 | < 1% |
| meta 이벤트 도달 p95 | 첫 `meta` SSE 이벤트까지 | < 1초 |
| 스트림 완료 p95 | `done` 이벤트까지 | 보고 |
| 메모리 증가량 (S3) | soak 30분 후 `docker stats` RSS 증가 | < 10% |
| 연결 누수 (S3) | 종료 후 열린 연결 수 | 0 |
| CPU 크레딧 잔량 (S1) | CloudWatch `CPUCreditBalance` | 보고 |

**S4 비기능 검증**

- 비로그인 5회 → 6번째 요청 `429 GUEST_QUOTA_EXCEEDED` 반환 확인
- 로그인 일일 100회 → 101번째 `429 DAILY_QUOTA_EXCEEDED` 반환 확인

**산출물**: VU별 오류율·latency 그래프, `docker stats` 시계열, 동시 스트림 한계 수치 보고
