## 1. 프로젝트 개요

### 1.1 문제 정의

#### 1.1.1 문제 배경

개발 학습 환경에서 학습자는 공식 문서보다 블로그·커뮤니티·영상 등 2차 자료와 범용 LLM에 의존한다. 이 자료들은 접근성이 높지만 **어느 버전 기준의 정보인지**를 사용자가 판단하기 어렵다.

LangChain은 이 문제가 가장 극명한 사례다. 0.x 시절의 체인·에이전트 API는 v1.0에서 `langchain` 패키지에서 제거되어 `langchain-classic`으로 이동했고, 에이전트 구성 방식 자체가 바뀌었다. 블로그와 LLM 답변에는 두 시대의 코드가 섞여 있다.

실제로 생성형 AI에 오류 수정을 요청했을 때, 단순한 버전 변경으로 해결되는 문제임에도 불필요하게 수십 줄의 코드가 추가되어 돌아오는 경험을 했다. 이는 질문을 아무리 구체적으로 작성해도 해결되지 않는 한계이며, **모델이 참조하는 정보가 버전 단위로 통제되어 있지 않기 때문**에 발생하는 구조적 문제다.

```python
# LangChain 0.3 기준 코드 — 블로그·LLM 답변에 여전히 다수 존재
from langchain.chains import LLMChain  
# 1.x 에서 ImportError (langchain-classic으로 이동)

# LangChain 1.x 기준 코드
from langchain.agents import create_agent
agent = create_agent(model=..., tools=[...])
```

추가 문제:

- ChatGPT, Claude 등 기존 LLM은 학습 데이터 컷오프 이후의 API 변경을 충분히 반영하지 못할 수 있으며, 웹 검색 기반 시스템 역시 공식 문서·블로그·커뮤니티 정보가 혼재된 상태에서 답변을 생성하므로 버전 불일치 문제가 발생한다.
- 또한 답변의 근거 문서와 버전 기준이 명확히 제시되지 않아 사용자가 신뢰성을 검증하기 어렵다.
- LLM은 버전을 구조적으로 분리하지 않는다. 동일한 API 이름이 버전마다 다른 동작을 하는 경우, LLM은 이를 맥락 없이 혼합하여 답변한다.

#### 1.1.2 기존 방식 또는 서비스의 한계

| 도구 | 핵심 한계 | 버전 통제 |
| --- | --- | --- |
| ChatGPT / Claude | 학습 시점 이후 변경 반영 한계, 
여러 버전 지식이 혼재, 출처 불명확 | 없음 (프롬프트에 버전 명시해도 보장 없음) |
| Perplexity | 출처 제공하나 소스(블로그·공식) 혼재, 버전 필터 없음 | 없음 |
| 공식 문서 직접 탐색 | 정확하나 자연어 질의 불가, 
버전 간 비교는 사용자가 직접 | 사용자 수동 |
| Context7 | 버전별 문서를 IDE/에이전트 컨텍스트로 공급 | 있음. 단, 학습자용 웹 Q&A·버전 간 비교 UX·검색 품질 검증 구조 없음 |
| Kapa / Inkeep | 문서 기반 답변 + citation 제공 | 현재 버전 중심. 과거 버전 대비 비교 학습 기능 부재 |

**공통 한계:** 기존 도구는 버전 혼입 문제를 소스·검색·생성 세 층위로 분해하지 않고, 개별 층위만 부분적으로 해결한다.

- **L1 (소스 층위):** 버전별 문서가 서로 다른 저장소·포맷·URL 체계에 흩어져 있어, 수집 단계에서 버전이 뒤섞인다.
- **L2 (검색 층위):** 버전 구분 없이 검색하면 주제는 같고 API는 다른 청크가 섞인다.
- **L3 (생성 층위):** 검색이 깨끗해도 LLM이 사전학습 지식으로 다른 버전 코드를 섞어 쓴다.

#### 1.1.3 해결 목표

| 해결 과제 | 해결 방향 |
| --- | --- |
| 버전별 문서 소스 불일치 (L1) | 버전마다 Source Adapter를 두고 공통 스키마로 정규화. 수집 커밋 SHA 고정 |
| 검색 단계 버전 혼입 (L2) | 선택 버전 네임스페이스에서만 검색. 격리 유무의 차이를 E1으로 정량화 |
| 생성 단계 버전 혼입 (L3) | 근거 기반 답변 강제, 근거 부족 시 NO_CONTEXT 응답, 버전 정확도를 E3으로 정량화 |
| 출처 불명확 | 청크별 섹션 경로 + 불변 permalink 반환 |
| 버전 변화 학습 어려움 | v0.3 ↔ v1.x 비교 모드 (양쪽 근거 인용 필수) |
| 설계 판단 근거 부재 | 청킹·격리 방식·K값을 사전 정의한 결정 규칙과 실험(E1~E6)으로 선택 |

### 1.2 프로젝트 목표

- **공통 목표:** 검색 소스를 공식 문서로 고정하고 버전 네임스페이스를 구조적으로 분리하여, 출처가 보장된 버전별 Q&A를 제공한다.
    - **서비스 관점:** 사용자가 LangChain 버전(v0.3 / v1.x)을 선택하고 자연어로 질문하면, 해당 버전 공식 문서에서만 검색하여 근거 인용·섹션 경로·permalink와 함께 한국어 답변을 스트리밍한다.
    - **개발 관점:** 버전 혼입 문제를 L1·L2·L3 세 층위로 분해하고, 각 층위의 설계 효과를 실험(E1~E3)으로 정량 측정하여 설계 판단 근거를 수치로 제시한다.

| 목표 | 설명 | 성공 기준(측정 가능 지표) |
| --- | --- | --- |
| 검색 격리 효과 | 버전 격리 검색이 혼입을 줄임을 수치로 제시 | E1: 격리 조건 혼입 0건, 비격리 조건 혼입률 수치 보고 |
| 답변 버전 정확도 | 본 시스템이 범용 LLM보다 버전 오류를 줄임 | E3: 시스템(R2) 버전 오류율 < 범용 LLM(L0·L1), 절대값 20% 이하 |
| 출처 URL 정확성 | 반환 permalink가 실제 공식 문서 섹션을 지시 | permalink 자동 검증 100%, 섹션 일치 수동 검증 20건 중 18건 이상 |
| 청킹 전략 근거 | 전략 선택이 수치 기반임을 증명 | E2: 전략 A/B/C Hit@K 비교표 + 사전 정의 결정 규칙(실험 전 커밋) |
| 스트리밍 응답성 | 첫 토큰 응답 시간 | E5: 배포 환경 20회 측정, TTFT p50 ≤ 3초, p95 ≤ 5초 |
| 무료 인스턴스 용량 | 동시 사용 한계를 수치로 확인 | E6(k6): mock LLM 기준 10 VU에서 오류율 < 1% |
| 재현성 | 새 환경 기동 가능 | README 절차만으로 30분 이내 전체 서비스 기동 |

### 1.3 기대 효과

| 관점 | 기대 효과 |
| --- | --- |
| 사용자 | 선택한 버전의 공식 문서 근거로만 답을 받고, 원문을 즉시 검증 가능 |
| 기술 | "버전 혼입"을 소스·검색·생성 3층위로 분해하고 각 층위의 대응 효과를 정량 측정 |

#### 2.1.2 페르소나

**페르소나 A — 실용형 학습자**

- 이름/직업/상황: 학부 4학년 취준생. LangChain으로 RAG를 처음 구현 중. 블로그 코드를 따라 했지만 ImportError가 발생하고 LLM에 물어봐도 여전히 0.x 방식의 코드를 준다.
- 문제 상황: 어떤 버전 기준의 답변인지 알 수 없고, 버전 하나 차이로 전혀 다른 코드가 필요한데 이를 판단하기 어렵다.
- 니즈: 지금 사용하는 버전 기준으로 실제 공식 문서에서 확인된 동작 가능한 코드와 출처를 빠르게 확인하고 싶다.

**페르소나 B — 유지보수 개발자**

- 이름/직업/상황: LangChain 0.3 기반 RAG 서비스 운영 중인 주니어 개발자. 패키지 업데이트 후 기존 코드가 동작하지 않는 상황.
- 문제 상황: ChatGPT는 이전 버전 코드를 준다. 공식 문서를 뒤지면 어느 섹션을 봐야 하는지 모르겠다.
- 니즈: 0.3 기준과 1.x 기준을 나란히 비교해서 무엇이 바뀌었는지, 어느 공식 문서에 근거가 있는지 빠르게 확인하고 싶다.

#### 2.1.3 공통 니즈 요약

사용자는 LLM의 접근성(자연어 질의)은 원하지만, 버전 오류와 출처 불명확성은 원하지 않는다. **공식 문서의 정확성을 LLM의 편의성으로 포장하되, "이것이 어느 버전의 어느 문서 섹션에서 온 답변인가"를 투명하게 확인할 수 있어야 한다.**

### 2.3 시장성 및 근거

#### 2.3.1 시장/사용자 규모

이 프로젝트의 핵심 타겟은 LangChain을 학습 중인 개발자다. 중요한 것은 전체 시장 규모 자체보다, **"버전 정확성 문제를 겪는 사용자가 실재하고 지속적으로 증가하고 있는가"**이다.

- LangChain은 2023년 출시 이후 0.1 → 0.2 → 0.3 → 1.x 로 짧은 주기에 핵심 API가 크게 바뀐 대표 프레임워크다.
- GitHub stars 2024년 12월 기준 누적 약 96K, 월 2,800만 다운로드 (출처: Contrary Research — LangChain Business Breakdown, 2025.01).
- 버전 변경이 가장 잦은 프레임워크가 가장 빠르게 사용자가 늘고 있다는 것은, 버전 정확성 문제를 겪는 사용자 모수가 실재하고 증가함을 의미한다.

#### 2.3.2 경쟁 서비스 분석

| 서비스명 | 장점 | 핵심 한계 |
| --- | --- | --- |
| ChatGPT / Claude | 자연어 질의 가능, 폭넓은 지식 | 버전 혼합 답변, 출처 불명확, 컷오프 이후 변경 미반영 |
| Perplexity | 출처 URL 제공 가능 | 검색 소스 통제 불가, 버전 필터링 부재 |
| Context7 | 버전별 문서 제공, IDE/에이전트 연동 | 독립 웹 Q&A 불가, 버전 간 비교 기능 없음, 검색 품질 실험 구조 없음 |
| Kapa / Inkeep / Mintlify | B2B 문서 기반 답변 + citation | 학습자 대상 버전 비교 기능 부족 |
| DocsGPT / Onyx | 범용 knowledge source 기반 QA | 특정 프레임워크 버전 단위 분리·비교 기능 없음 |

#### 2.3.3 성장 가능성

문서 수집 파이프라인이 Source Adapter 인터페이스로 추상화되어 있어, PyTorch·Transformers·FastAPI 등으로 지원 프레임워크를 순차 확장할 수 있다. LangChain 검증 이후 동일 구조로 추가 비용이 낮게 확장 가능하다.

#### 2.3.4 관련 트렌드

- AI/ML 프레임워크의 급격한 버전 업데이트 주기 단축 (특히 LLM 애플리케이션 레이어)
- RAG 기반 LLM 애플리케이션 수요 증가
- 개발자 도구의 공식 문서 기반 AI 보조 요구 증가 (Context7, Cursor Docs 기능 등)

#### 2.3.5 차별화 포인트

기존 서비스들은 정확성과 접근성 중 하나만 제공하거나, 버전 혼입 문제를 특정 층위에서만 부분적으로 다룬다. 본 프로젝트의 차별화는 다음 네 가지다.

1. **검색 소스를 공식 문서로 고정** — 비공식 자료 개입을 수집 단계에서 원천 차단
2. **버전 네임스페이스 구조적 분리** — 버전을 "고려"하는 수준이 아니라 검색 단계에서 혼입 자체를 차단
3. **불변 permalink 출처 반환** — 사용자가 답변의 신뢰성을 직접 검증 가능
4. **3층위 실험적 검증** — 소스·검색·생성 각 층위의 설계 효과를 정량 비교하여 단순 구현이 아닌 실험 기반 설계 프로젝트로 차별화

## 3. 서비스

### 3.1 서비스 개요

- **서비스명:** ContextQ-RAG
- **서비스 소개:** AI/ML 프레임워크 학습자를 위한 버전 인식 공식 문서 기반 LLM Q&A 플랫폼. 사용자가 LangChain 버전(v0.3 / v1.x)을 선택하고 자연어로 질문하면, 해당 버전 공식 문서에서만 검색하여 근거 인용·섹션 경로·permalink와 함께 한국어 답변을 스트리밍한다. 동일 질문에 대한 두 버전 비교도 제공한다.

### 3.2 주요 기능 및 서비스

- **핵심 기능**
    1. 버전별 공식 문서 기반 RAG 검색 + 출처(섹션 경로·permalink) 반환
    2. SSE 스트리밍 응답 (출처 먼저 표시 → 답변 토큰 스트리밍)
    3. NO_CONTEXT 처리 (범위 밖 질문 시 LLM 미호출, 안내 메시지 반환)
    4. 멀티턴 대화 (질의 재작성으로 이전 맥락 반영)
    5. 버전 비교 모드 (v0.3 ↔ v1.x, 양쪽 근거 인용 필수)
    6. JWT 로그인 + 대화 이력 저장·조회
    7. 관리자: 인덱스 현황 대시보드 (버전별 커밋 SHA·문서·청크 수·수집일)
- **서비스 디자인 방향성:** 개발자 도구 성격의 SPA. 출처 카드(섹션 경로 + permalink)와 버전 전환 UX를 최우선으로 설계한다. 매 응답에 인덱스 스냅샷 커밋 SHA와 수집일을 표시하여 "어느 시점 기준의 답변인가"를 투명하게 한다.

### 3.3 사용자 흐름 (User Flow)

#### 3.3.1 일반 사용자 흐름

```
1단계. 진입
   ├─ 비로그인: 세션당 5회 제한, 단일 모드만, 이력 저장 없음 (브라우저 메모리 유지)
   └─ 로그인: 이력 저장·조회 가능

2단계. 프레임워크·버전 선택  ← GET /api/v1/meta/sources 응답으로 드롭다운 구성
   ├─ 단일 모드: 버전 1개 선택
   └─ 비교 모드: 버전 2개 선택 (compare_enabled=true 인 경우만 탭 활성화)

3단계. 질문 입력 및 답변
   ├─ 단일: meta 이벤트(출처 카드 먼저 표시) → token 스트리밍 → done
   ├─ 비교: A/B 각 요약 + 변경점(각 항목 양쪽 인용 번호) JSON 반환
   └─ NO_CONTEXT: 고정 안내 메시지 표시, 생성 LLM 미호출

4단계. 후속 질문 (선택)
   └─ 대화의 프레임워크·버전·모드는 고정. 버전 변경 시 새 대화 시작
```

#### 3.3.2 관리자 흐름

```
관리자 로그인 (ROLE_ADMIN)
  → 인덱스 현황 대시보드
    (버전별 활성 인덱스, 커밋 SHA, 문서·청크 수, 수집일 표시)
  → (P2) 재수집 트리거 실행 (로컬·스테이징 전용)
  → 수집 이력 확인
```

#### 3.3.3 사용자 흐름 확장

```
로그인 사용자
  → 대화 이력 목록 조회 (updated_at 내림차순)
  → 특정 대화 상세 조회 (메시지·출처 포함)
  → 해당 대화 이어서 질문 (버전·모드 고정 유지)
```

### 4.2 설계 판단 근거

**결정 1 — Spring Boot(업무) + FastAPI(AI) 이중 서버 구조**

- 선택: 인증·세션·이력은 Spring Boot, RAG 파이프라인은 FastAPI로 분리
- 근거: Python 생태계(LangChain, OpenAI SDK)와 Java 생태계(Spring Security, JPA)는 각자의 영역에서 성숙도가 다르다. ai-server를 사용자 정체성과 무관한 무상태 서비스로 설계하면, 평가 스크립트가 서비스 코드와 동일한 검색 경로를 호출할 수 있다("실험한 시스템 = 배포한 시스템" 보장).
- 트레이드오프: 서비스 간 통신 오버헤드, SSE 이중 중계, 배포 복잡도 증가. Docker Compose 내부망으로 통신하여 외부 노출 없이 운영하고, 타임아웃 3종(연결 3초·첫 이벤트 15초·유휴 30초)으로 장애 전파를 차단한다.

**결정 2 — 버전별 Source Adapter 구조 + 커밋 SHA 고정 수집**

- 선택: LangChain v0.3은 `langchain-ai/langchain` v0.3 브랜치(`docs/docs/`, Docusaurus 포맷), v1.x는 `langchain-ai/docs` main 브랜치(`src/oss/`, Mintlify 포맷)에서 각각 수집. 각 저장소를 sparse checkout 후 커밋 SHA를 기록·고정.
- 근거: PoC에서 `langchain-ai/docs` main 1,852개 `.mdx` 파일을 수집하고 26개 섹션 파싱·152청크 생성(전략 B 기준)까지 완료하여 파이프라인이 성립함을 확인했다. 그러나 수집 검증 과정에서 이 저장소가 v0.3이 아닌 v1.x 문서임을 발견했다. 버전마다 저장소·포맷·URL 체계가 다르기 때문에, 단일 수집기로는 소스 수준에서 버전이 뒤섞인다. main 브랜치 추적은 재현성을 파괴한다.
- 트레이드오프: Source Adapter 2개 구현, 노트북(`.ipynb`) 파서 추가. 커밋 고정으로 "최신" 문서를 약속하지 않는 대신 "어느 스냅샷 기준인가"를 투명하게 표시한다.

**결정 3 — Chroma ai-server 내장 (PersistentClient) 모드**

- 선택: 별도 서버 컨테이너가 아니라 ai-server 프로세스 내부에서 Chroma PersistentClient 사용
- 근거: 무료 인스턴스 메모리 예산(2GiB)에서 프로세스 1개를 절감한다. 코퍼스 규모(수만 청크 이하)에서 검색 성능은 충분하다. 볼륨 마운트로 데이터를 보존하고, 서버 모드로의 전환은 클라이언트 설정 변경만으로 가능하도록 VectorStore 어댑터 경계를 유지한다.
- 트레이드오프: uvicorn 워커를 1개로 고정해야 한다(단일 프로세스 접근 제약). 수평 확장이 불가능하다. E6에서 동시 스트림 한계를 측정해 수치로 기록한다.

**결정 4 — 운영 환경에서 수집·임베딩 금지, 스냅샷 복원만 수행**

- 선택: 인덱스는 로컬에서 빌드·검증 후 스냅샷으로 내보내고, 운영 EC2는 복원과 활성화만 수행
- 근거: 문서 수집(GitHub sparse checkout + 파싱)과 임베딩(OpenAI API 다수 호출)은 메모리·CPU 집약 작업이다. 무료 인스턴스에서 실행하면 서비스 중단 위험과 CPU 크레딧 소진 위험이 동시에 발생한다. 인덱스를 버전 관리되는 산출물로 다루면 롤백이 단순해지고 재현성이 높아진다.
- 트레이드오프: 운영 환경에서 관리자 재수집 불가(조회 전용). 관리자 재수집 버튼(P2)은 로컬·스테이징 전용으로 제한하고, 운영 프로필에서 실행 시 `403 FORBIDDEN_IN_PROFILE`을 반환한다.

**결정 5 — SSE + fetch/ReadableStream**

- 선택: FastAPI → Spring Boot → React 구간을 SSE로 전달. 클라이언트는 `EventSource` 대신 `fetch + ReadableStream` 사용
- 근거: LLM 토큰 단위 스트리밍은 단방향 서버→클라이언트 푸시이므로 WebSocket 양방향이 불필요하다. `EventSource` API는 Authorization 헤더 커스터마이징·POST 요청이 불가능하여 JWT를 전달할 수 없다. SSE 이벤트를 `meta → token* → done` 순서로 설계하면 출처 카드를 답변 생성 전에 먼저 표시할 수 있다.
- 트레이드오프: 재연결 로직 직접 구현 필요. 단순화를 위해 재연결은 하지 않고 실패 시 부분 답변 표시 + 재질문 유도로 처리한다. nginx `proxy_buffering off` + `X-Accel-Buffering: no` 설정이 필수다.

**결정 6 — AWS 무료 플랜, 단일 EC2 t3.small**

- 선택: 외부 지원 없음. 무료 플랜 크레딧 범위(가입 100달러 + 활동 보너스 최대 100달러) 내에서 운영. 기본 인스턴스 `t3.small`(2GiB), 부하 테스트·최종 시연 기간에만 `c7i-flex.large`(4GiB)로 일시 증설.
- 근거: 시연·평가 트래픽 규모에서 해결해야 할 확장성 문제가 없다. 판단을 추정이 아닌 E6(k6) 측정으로 대체한다. 각 확장 단계가 설정 수준으로 끝나도록 서비스 경계를 설계했다.
- 트레이드오프: 메모리 2GiB, CPU 크레딧 스로틀링, 단일 장애점, 크레딧 소진 시 계정 정지. 크레딧 소진이 발표 기간에 발생하면 서비스 중단으로 이어지므로, 주 1회 잔여 크레딧 점검·Budgets 알림, 시연 영상·로컬 환경 백업을 준비한다.

**결정 7 — 버전 격리 방식: 컬렉션 분리**

- 선택: 버전별 Chroma 컬렉션 분리 (langchain_v03_run{id}, langchain_v1x_run{id})
- 근거: 1인 개발에서 메타데이터 필터 3조건 중 하나를 빠뜨리면 혼입이 발생한다. 컬렉션 분리는 필터 누락을 구조적으로 차단한다.
- 트레이드오프: 컬렉션 수 증가, 교차 버전 질의 불가. 졸업작품 범위에서 교차 버전 질의 기능은 없으므로 무관하다.

### 4.3 데이터 흐름

**단일 버전 모드 RAG 처리 흐름**

```
1. 사용자 질문 + 버전 → React
2. React → Spring Boot (POST /api/v1/chat, fetch+ReadableStream)
3. Spring Boot: JWT 검증·비로그인 카운트 → WebClient → FastAPI POST /internal/v1/chat/stream
4. FastAPI:
   a. (멀티턴) 이전 3턴으로 질의 재작성 (rewritten_query 기록)
   b. 질문 임베딩 (text-embedding-3-small)
   c. Chroma 검색: 컬렉션(langchain_v03_run{id} / langchain_v1x_run{id}) 직접 지정 + ingest_run_id 필터, Top-K
   d. 유사도 < τ 이면 → NO_CONTEXT 응답 (생성 LLM 미호출)
   e. meta 이벤트 전송 (출처 목록, 스냅샷 커밋 SHA)
   f. GPT-4o-mini 스트리밍 (근거 기반 프롬프트, temperature=0)
   g. token 이벤트 스트리밍
   h. done 이벤트 (사용량·단계별 지연)
5. Spring Boot: FastAPI SSE → 클라이언트 SSE 중계 (proxy_buffering off)
6. Spring Boot: 스트림 완료 시 메시지·출처 DB 저장 (로그인 사용자)
```

**오프라인 인덱스 빌드 흐름 (로컬에서 실행)**

```
[소스 수집]  git sparse-checkout (v0.3: langchain-ai/langchain@v0.3·docs/docs/
                                 v1.x: langchain-ai/docs@main·src/oss/)
→ 커밋 SHA 기록
→ (1.x만) 스니펫 인라인 확장 (import + <X /> → 스니펫 본문 대체, 없으면 태그 제거 + 누락 목록 기록)
→ 전처리: frontmatter 제거·:::js 블록 제거·JSX 태그 제거·노트북 직렬화
→ 섹션 분리 (#/## 헤더, heading_path 생성)
→ 청킹 (전략 E2 결과에 따라 선택)
→ 임베딩 (text-embedding-3-small)
→ Chroma 저장 (컬렉션: langchain_v03_run{id} / langchain_v1x_run{id}, ingest_run_id 필터)
→ VALIDATING (청크 수·메타데이터·permalink·스모크 질문)
→ 스냅샷 tar → EC2 복원 → 활성화
```

### 5.2 핵심 기능 상세

#### 5.2.1 버전별 공식 문서 기반 RAG 검색

- 문제: 기존 LLM은 버전을 구조적으로 분리하지 않고 답변을 생성한다.
- 동작 방식: 활성 인덱스(`ingest_run_id`)를 기준으로, 선택한 framework + version 조건에서만 벡터 검색한다. 유사도 임계값 τ 미만이면 LLM을 호출하지 않고 NO_CONTEXT 응답을 반환한다. Top-K는 E2 결과로 확정(초기값 5).
- 입력 데이터: 질문 텍스트, framework, version, 대화 이력(멀티턴 시), ingest_run_id
- 출력 데이터: Top-K 청크(text + heading_path + permalink + cosine similarity)
- 예외 상황: 상위 유사도 < τ → NO_CONTEXT (LLM 미호출, 안내 메시지 반환)
- 선택 근거: 검색 소스를 공식 문서로 고정하고 버전 범위를 제한하는 것이 L2 층위 설계의 핵심이다.
- MVP 포함 여부: Y
- 인수 기준: E1에서 격리 조건 혼입 0건, Q-oos 10건 중 8건 이상 NO_CONTEXT 응답

#### 5.2.2 출처 섹션 경로 + Permalink 반환

- 문제: 기존 LLM은 답변 근거를 제시하지 않아 정보의 신뢰성을 검증할 수 없다.
- 동작 방식: 검색된 청크의 `heading_path`(예: "Agents > Tools > Defining tools"), `permalink`(커밋 SHA 고정 GitHub URL)를 `meta` SSE 이벤트로 답변 생성 전에 먼저 전송한다.
- 입력 데이터: 검색된 Top-K 청크 메타데이터
- 출력 데이터: `meta` 이벤트 내 `sources[]`(rank, heading_path, permalink, similarity)
- 선택 근거: permalink는 커밋 SHA 고정으로 불변이므로 자동 검증(HTTP 200)이 가능하다. site_url을 주 출처로 두면 문서 사이트 구조 변경 시 URL이 무효화된다.
- MVP 포함 여부: Y
- 인수 기준: permalink 자동 검증 100%, 섹션 일치 수동 검증 20건 중 18건 이상(라인 앵커) / 15건 이상(파일 단위 폴백 시), W1 결과로 자동 결정

#### 5.2.3 멀티턴 대화 (질의 재작성)

- 문제: 단발 Q&A는 학습 목적 서비스에서 자연스러운 연속 질문 패턴을 지원하지 못한다.
- 동작 방식: 대화의 framework·version·mode는 생성 시 고정한다. 후속 질문이 있으면 이전 3턴(6메시지)을 참조해 소형 프롬프트로 질의를 재작성하고, `rewritten_query`를 meta 이벤트와 DB에 기록한다.
- MVP 포함 여부: Y
- 인수 기준: 후속 질문 5건 중 4건 이상에서 재작성 쿼리가 이전 맥락을 반영함을 수동 확인

#### 5.2.4 버전 비교 모드

- 문제: 단순 Q&A로는 버전 간 API 변경을 명시적으로 학습하기 어렵다.
- 동작 방식: 동일 질문을 두 버전 인덱스에 각각 검색 → 두 결과를 단일 프롬프트에 주입 → LLM에 버전 간 차이 설명 요청 → 구조화 JSON 반환(각 버전 요약 + 변경점 목록, 각 항목에 양쪽 인용 번호). 한쪽 근거 없으면 "해당 버전 문서에서 근거 없음" 표시.
- 선택 근거: Breaking Change가 실제로 있는 v0.3 ↔ v1.x에만 적용. 마이그레이션 가이드(`migrate/langchain-v1`)가 v1.x 코퍼스에 포함되어 있어 자연스럽게 검색된다. 비스트리밍 JSON으로 범위 통제.
- MVP 포함 여부: Y (비스트리밍)
- 인수 기준: 비교 질문 10건 수동 평가에서 존재하지 않는 인용 번호 0건, 변경점에 양쪽 근거 인용

#### 5.2.5 관리자 페이지

- 문제: RAG 시스템은 인덱싱된 데이터 상태가 검색 품질을 좌우하므로, 현재 인덱스 기준이 무엇인지를 가시화할 필요가 있다.
- 동작 방식: 버전별 활성 인덱스(커밋 SHA·수집일·문서 수·청크 수), 수집 이력 조회. 운영 환경에서는 조회 전용, 로컬·스테이징에서만 재수집 트리거 사용 가능.
- 선택 근거: 발표·심사 시 "어떤 문서가 몇 개 청크로 인덱싱되어 있는가"를 정량적으로 보여줄 수 있어 평가에도 유효하다.
- MVP 포함 여부: Y (조회), P2 (재수집 트리거)
- 인수 기준: 버전별 커밋 SHA·청크 수 표시, 비관리자 접근 403 반환

### 5.3 MVP 범위 (필수 구현)

- **버전별 RAG 검색 + 출처 반환** — 이것이 없으면 L2 설계 주장이 증명되지 않는다.
- **NO_CONTEXT 처리** — 이것이 없으면 "범위 내에서만 답한다"는 근거 제한 전략이 구현되지 않는다.
- **SSE 스트리밍** — 신청서에 명시된 핵심 기술 요소이며, E5 측정 기준.
- **버전 비교 모드** — L1(소스 분리 수집)의 결과물을 사용자에게 직접 보여주는 기능.
- **JWT 로그인 + 대화 이력** — 사용자 기능 완성.
- **Source Adapter (v0.3, v1.x) + 인덱스 스냅샷 복원** — 데이터 레이어 없이는 나머지 기능이 전부 공허하다.

### 5.4 확장 기능 (2단계)

- 관리자 재수집 트리거 UI (현재는 CLI)
- 답변 심볼 검증기 E4 (API 심볼 사전 대조)
- RAGAS 기반 자동 RAG 평가 파이프라인
- 지원 프레임워크 확장 (PyTorch, Transformers — Source Adapter 인터페이스 활용)

### 5.5 범위 외 기능 (의도적 제외)

- **자체 LLM 학습·파인튜닝** — 제외 이유: 이 프로젝트의 핵심은 LLM 자체가 아니라 RAG 파이프라인 설계·검증. 파인튜닝은 버전 혼입 문제(L2·L3)와 직접 연결되지 않음.
- **실시간 문서 동기화 스케줄러** — 제외 이유: 수동 스냅샷 복원으로 충분. 스케줄러 추가 시 운영 인스턴스에서 수집·임베딩을 실행해야 하는 메모리 문제가 재발.
- `LangChain 외 프레임워크 및 langgraph 패키지 문서 (졸업작품 범위 내)` — 제외 이유: 평가 레이블링 비용이 배가되어 실험의 깊이가 얕아짐. Source Adapter 인터페이스로 확장 경로만 제시. langgraph는 별도 버전 체계를 가지며 관련 질문은 NO_CONTEXT로 처리.
- **하이브리드 검색(BM25)·리랭커** — 제외 이유: 실험 변수를 늘림. 보고서 "향후 과제"로 기술.
- **Redis, Kubernetes, 모니터링 스택** — 제외 이유: 규모 대비 과도.
- **이메일 인증, 소셜 로그인, 회원 탈퇴** — 제외 이유: 핵심 가치와 무관, 일정 내 구현 가치 낮음.
- **IDE 플러그인 / MCP 서버** — 제외 이유: 웹 서비스 완성도 우선.

### 8.2 필수 테스트 케이스

**검색 격리 (핵심)**

- 비격리(N) 조건: v0.3·v1.x 청크를 단일 컬렉션에 넣고 필터 없이 검색 → 혼입률 측정(E1-N)
- 격리(F) 조건: 버전 필터 적용 검색 → 혼입 0건 확인(E1-F 또는 E1-C)
- NO_CONTEXT: Q-oos 10건 질문 시 8건 이상 LLM 미호출 확인

**출처 정확성**

- 반환 permalink 자동 검증(HTTP 200) 100%
- 섹션 일치 수동 검증 20건 (permalink로 원문 접속하여 heading_path와 일치 여부 확인)

**청킹 전략 비교 (E2, 블라인드)**

- Q-ret 40문항에 전략 A(CharacterTextSplitter)·B(RecursiveCharacterTextSplitter)·C(구조 인식, 코드 펜스 원자 단위) 각각 적용
- Hit@K, MRR@K, Precision@K (K=3,5,8) + 평균 컨텍스트 토큰 수
- 결정 규칙: Hit@5 최고 전략 채택. 1·2위 차이 3%p 미만이면 평균 토큰이 적은 전략. K는 증가폭 < 2%p인 최소 K.
- 규칙은 실험 전(`eval-v1` 태그 이전)에 `eval/decision_rules.md`에 커밋하여 사후 수정 불가

**답변 버전 정확도 (E3, 블라인드)**

- Q-shared 20문항 × 버전 2 = 40문항 × 4조건(L0·L1·R1·R2) = 160답변. temperature 0, 동일 모델
- 레이블: 버전 오류 여부(0/1), 근거 충실성(R1·R2만), 답변 유용성(0~2)
- 조건 라벨 가리고 2인(지도교수·1인 외부) 독립 레이블링, 불일치 건 판정

**멀티턴 컨텍스트**

- "LCEL이란?" → "그걸로 RAG 구성하려면?" → 2번째 답변에 1번 맥락 반영 여부

### 8.4 정성 검증

- **청킹 전략 비교:** Hit@K 외에, 검색된 청크의 코드 블록 분리 여부·맥락 완결성을 정성 평가. 전략 C(구조 인식) 선택 근거를 정성·정량 양면에서 기술.
- **프롬프트 설계 근거:** 근거 제한·인용 번호·한국어 유도 전략을 문서화하고, 프롬프트 버전 변경 전후 답변 품질을 동일 질문셋으로 비교. 변경 이력은 `prompt_version`으로 기록.
- **E3 블라인드 평가 일치율:** 레이블러 간 불일치 비율과 판정 근거 공개. 표본 크기 한계를 타당성 위협으로 명시.
- **PoC 전제 재검토 서술:** v0.3 문서를 `langchain-ai/docs`에서 수집한다는 PoC 전제가 사실과 다름을 발견한 과정, 그리고 Source Adapter 설계로 대응한 판단을 보고서 "문제 재정의" 절에 기록. 이 과정이 설계 판단 능력을 보여주는 가장 중요한 서술 중 하나다.

### 8.5 설계 방어 포인트

**예상 질문 1 — "LLM에 '버전 X 기준으로 답해줘'라고 하면 되지 않는가?"**

- 대응 논리: E3의 L1 조건(범용 LLM + 버전 명시 프롬프트)이 정확히 이 질문에 대한 실측이다. 프롬프트는 모델이 어떤 지식을 떠올릴지를 "요청"할 뿐 통제하지 못한다. L1 대비 R2(격리 RAG)의 버전 오류율 차이를 수치로 제시한다. 결과가 기대와 다르더라도 그대로 보고하고 원인을 분석한다.

**예상 질문 2 — "메타데이터 필터로 혼입 0은 당연한 결과 아닌가?"**

- 대응 논리: 맞다. 그래서 E1의 핵심 비교는 격리 방식 간이 아니라 "격리 없음(N) 대비"이다. 격리가 없을 때 혼입이 얼마나 발생하는지를 측정해야 격리의 필요성이 증명된다. 격리 방식 간 선택은 정확도가 아니라 필터 누락 가능성·교체 용이성·지연이라는 공학적 기준으로 결정하고, 그 근거가 ADR-004에 있다.

**예상 질문 3 — "검색이 깨끗해도 LLM이 다른 버전 코드를 쓰면?"**

- 대응 논리: 이것을 L3(생성 층위) 문제로 명시적으로 분리했다. E3에서 R2의 잔여 오류율로 크기를 측정했고, 근거 제한 프롬프트·NO_CONTEXT·(E4) 심볼 검증으로 대응한 결과를 제시한다. "원천 차단"이 아니라 "검색 단계에서 차단, 생성 단계에서 측정·완화"가 정확한 주장이다.

**예상 질문 4 — "청킹 전략 선택 근거가 무엇인가? 결과를 보고 고른 것 아닌가?"**

- 대응 논리: 결정 규칙(Hit@5, 3%p 동률 기준, 토큰 비용)을 실험 전에 `eval-v1` 태그 이전 커밋으로 확정했다. 커밋 이력으로 선후 관계를 확인할 수 있다. gold는 섹션 단위라 청킹 전략 간 공정 비교가 가능하다.

**예상 질문 5 — "왜 v0.2가 아니라 v0.3 ↔ v1.x인가?"**

- 대응 논리: v0.2 → v0.3의 Python breaking change는 Pydantic 2 전환이 사실상 전부여서 학습자가 겪는 API 단절이 없다. 또한 PoC에서 `langchain-ai/docs`를 v0.3 문서라고 가정했으나, 실제로는 v1.x 문서임을 저장소 직접 확인으로 발견했다. 이 발견 과정을 문제 재정의로 기록했으며, 실제 단절이 발생하는 v0.3 ↔ v1.x를 비교 대상으로 바꾸는 것이 더 의미 있는 설계 결정이다.

**예상 질문 6 — "무료 인스턴스 하나로 서비스가 되는가?"**

- 대응 논리: 시연·평가 트래픽 규모에서 확장성 문제는 존재하지 않는다고 판단했다. 판단을 추정이 아닌 E6(k6) 측정으로 대체했다. 동시 스트림 한계와 병목 자원을 수치로 기록했고, 측정값이 기준을 초과하면 어떤 순서로 전환하는지를 ADR-011에 정의했다. 각 전환 단계가 설정 수준으로 끝나도록 서비스 경계를 설계했다.

### A. AWS 무료 플랜 메모리 예산 (t3.small, 2GiB)

| 구성요소 | 설정 | 예상 상주 메모리 |
| --- | --- | --- |
| OS + Docker 데몬 | — | 약 300MB |
| nginx | worker 1 | 약 20MB |
| PostgreSQL | `shared_buffers=64MB`, `max_connections=20` | 약 120~180MB |
| backend (Spring Boot) | `-Xmx320m -XX:MaxMetaspaceSize=128m`, Tomcat `max-threads=40` | 약 450~550MB |
| ai-server + 내장 Chroma | uvicorn 1 worker, HNSW 인덱스 메모리 적재 | 약 350~700MB (청크 수에 비례) |
| **합계** |  | **약 1.25~1.75GB** |
| 스왑 | 2GiB, `vm.swappiness=10` | OOM 방지 안전망 |

W5 배포 직후 `docker stats` 실측값으로 이 표를 교체한다.

### B. 비용 추정

- **임베딩:** 코퍼스 토큰 수 × 전략 3종 × `text-embedding-3-small` 단가. W1에 실측해 `docs/data-sources.md`에 기록.
- **E3 생성:** 160건 × 2회(비결정성 확인). 평가 응답 캐시(`eval/cache/`)로 재실행 비용 0.
- **AWS:** 운영 기간(W6~W9, 약 1개월) 기준 30~40달러 예상. 가입 크레딧 100달러 이내.
- **부하 테스트:** mock LLM으로 OpenAI 호출 없음. S0 smoke(실제 LLM 20회)만 발생.
- **운영 상한:** OpenAI 대시보드 월 사용 한도 설정, AWS Budgets 알림 50%·80%.
